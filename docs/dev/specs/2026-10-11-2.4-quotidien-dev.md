# 2.4 — Reprendre un ticket jusqu’à sa livraison (D67)

Le suivi reste local et sans IA. OKB retrouve les faits du travail ; il ne remplace ni Jira ni GitHub et ne transforme pas une fusion en livraison.

| Identifiant | Contrat technique |
|---|---|
| F2.4-01 | Brief corrigible : objectif, dernière action, essais échoués avec conditions et prochaine étape. Disponible dans le détail du ticket, le CLI et le brief de session existant. |
| F2.4-02 | Observations séparées pour travail, PR/revue, vérifications, attente et livraison par environnement. « Inconnu » est explicite ; chaque déclaration sauvegardée a une origine et une date. |
| F2.4-03 | Tests, documentation, recette et confirmation visibles. Un critère marqué obligatoire et encore inconnu/à vérifier empêche la clôture du travail. Un critère peut être écarté explicitement. |
| F2.4-04 | Essai conservé avec approche, conditions, résultat et prochaine piste facultative ; il rejoint le journal du ticket. |
| F2.4-05 | Aujourd’hui reprend les contrôles de fraîcheur existants : code cité changé, citation disparue ou fichier supprimé. Une note est à revérifier, pas déclarée fausse. |
| F2.4-06 | Une note réutilisée sur un ticket garde son chemin, titre et SHA de révision, la raison et la date. Sa réutilisation apparaît dans le journal. |
| F2.4-07 | Lecture d’une PR GitHub explicitement demandée via la session `gh` existante, sur serveur/dépôts autorisés. Jira : instantané fourni par la personne, identifié comme déclaré ; lecteur Jira externe à valider. |

## États et fin du travail

- Travail : `unknown`, `in-progress`, `done`.
- PR/revue : `unknown`, `not-open`, `draft`, `open`, `review`, `approved`, `changes-requested`, `merged`, `closed`.
- Vérifications : `unknown`, `pending`, `passed`, `failed`.
- Attente : `unknown`, `none`, `waiting`, `blocked`.
- Livraison, pour chaque environnement : `unknown`, `pending`, `deployed`, `verified`, `failed`.

La production commence inconnue. Déclarer une livraison en staging ne change pas la production. Terminer le travail ne change pas la PR, la CI, l’attente ou la livraison. Une observation Github renseigne seulement PR/revue et vérifications ; elle ne clôture pas le travail. Des vérifications absentes, ignorées ou non reconnues restent inconnues.

Les quatre repères initiaux restent facultatifs pour les tickets migrés et pour préserver le comportement 1.5. La personne définit les critères réellement obligatoires. Le garde porte sur ces critères déclarés ; il n’exécute pas les tests, ne prouve pas la recette et ne certifie pas une livraison. La clôture et les lectures/configurations externes exposées au moteur sont des actes réservés à la personne.

## Stockage, frontières et compatibilité

Migration SQLite **7**, ajoutée après conversations et compréhension : tickets, détails, observations, critères, essais et réutilisations. Les fichiers JSON 1.5 sont validés puis importés ensemble une seule fois ; ni les JSON ni leur texte original ne sont supprimés ou réécrits. Les champs inconnus des anciens enregistrements sont conservés. Une archive invalide bloque l’import sans import partiel. Les futures modifications vont dans SQLite ; les JSON restent une archive et ne constituent pas une deuxième source de vérité. Les anciennes versions ne doivent pas écrire simultanément dans ce profil migré.

Après application humaine de la proposition de fusion d’une KB de repo dans un espace, le transfert reprend les tickets courants associés au repo et leurs détails, états, critères, essais et réutilisations. Le texte privé et les chemins de notes réutilisées suivent leur destination. Le profil source est conservé ; une référence ou un texte déjà présents avec un autre contenu provoquent un conflit explicite sans écrasement. Le transfert SQLite est transactionnel ; les copies de textes privés sont précontrôlées et peuvent être reprises après interruption.

`ticket start/note/done/list/commit` et le suivi des branches/commits restent disponibles. `ticket done` prépare toujours ses faits pour le parcours de connaissance existant ; `ticket close` clôt seulement le travail local. Aucune de ces nouveautés ne rédige une note, n’approuve une proposition ou n’applique un changement dans la KB.

Le module dev habite `src/work/`, notamment `operations.ts`. Le registre commun le raccorde aux adaptateurs. Aujourd’hui reçoit les notes à revérifier par `ProjectSource.notesToRecheck` : le cœur n’importe pas le module dev. Le cache de fraîcheur expire après 15 secondes et invalide immédiatement sur nouveau HEAD/note ; un arbre Git modifié est revérifié à chaque lecture. Aucun scan du code, appel IA ou lecture externe implicite n’est ajouté.

Les limites locales sont 100 critères, 200 essais et 500 réutilisations par ticket. Elles refusent de nouvelles lignes sans supprimer l’historique. Les métadonnées des notes verrouillées sont exclues des nouveaux résultats de réutilisation exposés aux agents et du journal commun ; le détail personnel conserve son historique. La sauvegarde SQLite existante inclut toutes les nouvelles tables.

## Contrat commun

Opérations `tickets.list/get/start/brief/state/criterion/attempt/reuse/close`, `tickets.github.status/configure`, `tickets.github` et `tickets.jira`. L’API locale expose `/api/tickets`, `/api/ticket` et les routes `/api/ticket/{brief,state,criterion,attempt,reuse,close,github,jira}`. `GET/POST /api/ticket/github/config` affiche ou modifie l’autorisation complète ; `POST /api/tickets/start` démarre un suivi. Toutes les mutations de suivi renvoient le détail actualisé ; la configuration renvoie sa valeur, sans identifiant de connexion ni secret.

La configuration `connectors.github` est désactivée par défaut et limitée à `host` et `repositories`. La politique `allowedConnectors` peut refuser GitHub. Le processus exécute uniquement `gh pr view <n> --repo <host>/<owner>/<repo> --json …`, sans shell, connexion ni écriture distante. Il utilise la session déjà configurée par la personne, avec bornes de temps et de sortie. Une réponse invalide n’écrase pas les observations antérieures ; stderr n’est pas recopié dans la réponse API. L’instantané conserve l’URL canonique et la date de lecture ; ce sont des faits lus, pas une autorité d’écriture sur la KB.

Sources techniques vérifiées le 11 octobre 2026 : [champs et options de `gh pr view`](https://cli.github.com/manual/gh_pr_view), [environnement de GitHub CLI](https://cli.github.com/manual/gh_help_environment). Les tests utilisent un lecteur fictif ; ils ne valident pas un compte connecté ni les droits d’un dépôt réel.

## Vérification et porte d’usage

Les tests couvrent archive/migration, concurrence, états indépendants, critères, essais, réutilisation et journal, fraîcheur après commit, garde d’acteur, réponse GitHub invalide et instantané Jira déclaré. Le parcours du CLI compilé exerce les mêmes opérations dans des processus distincts. Les tests de frontière du module restent verts sans ajouter de dette autorisée.

La reprise réelle en moins d’une minute et l’absence d’oubli de livraison pendant un mois restent à mesurer auprès des personnes. Le lecteur Jira externe et un compte GitHub réel autorisé restent des vérifications distinctes.
